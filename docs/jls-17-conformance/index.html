      JLS 17 Conformance

      This page reviews JLS Chapter 17: Threads and Locks against Juno. The examples live in io.github.jabrena.juno.language.concurrency. Each board entry point is intentionally small, prints one observable result, allocates its state once at startup, and does not allocate in its worker loops.

      A successful run demonstrates one concrete execution. It cannot prove that every execution allowed by the Java Memory Model is implemented correctly. In particular, a stress test that does not observe a permitted data-race outcome does not make the racy program correct. The deterministic examples therefore assert required outcomes; the one deliberately racy final-field example treats failure to observe the published reference as allowed.

      Locks and higher-level coordination objects

      JLS 17 specifies the memory-ordering primitives (monitors, volatile access, thread start/join and interruption); it does not make Semaphore, CountDownLatch or the other java.util.concurrent classes language primitives. The examples make that boundary visible:

      Example Object demonstrated Target
      Locks Concrete ReentrantLock, reentrancy, tryLock, and finally/unlock Board-ready on UNO R4 WiFi, UNO Q and UNO WiFi Rev2
      Atomics AtomicInteger, AtomicLong, AtomicBoolean, compareAndSet and getAndSet Board-ready on UNO R4 WiFi, UNO Q and UNO WiFi Rev2
      Semaphores Counting permits JVM-only
      CountDownLatchExample One-shot completion gate JVM-only
      PhaserExample Reusable phase barrier JVM-only
      CyclicBarrierExample Reusable barrier and barrier action JVM-only
      ExchangerExample Two-party value exchange JVM-only
      ReadWriteLockExample Separate read and write locks JVM-only
      BlockingQueueExample Blocking producer/consumer queue JVM-only

      The board-safe BoundedBuffer shows the replacement pattern: a concrete ReentrantLock, a non-blocking offer/poll, and Thread.yield() while the caller retries. The compiler rejects the JVM-only classes' higher-level APIs instead of silently changing their blocking or fairness semantics. Their JUnit checks still run on OpenJDK, so each object has a focused executable example and a deterministic assertion.

      Clause-to-example matrix

      JLS clause Juno status Focused evidence
      17.1 Synchronization Monitor blocks are supported and reentrant. Normal and abrupt block exit emit monitor release. Synchronized methods are rejected. MonitorHappensBefore prints monitor value 42.
      17.2 Wait sets and notification Board objects have monitors but Juno does not expose JVM wait-set operations. The four following rows retain runnable JVM examples and mark the board boundary explicitly.
      17.2.1 Wait Object.wait is not lowered. On the JVM it requires monitor ownership, releases all of that thread's acquisitions of the monitor, may wake spuriously, and reacquires the same number before returning or throwing. WaitNotification.await uses the required guarded while loop.
      17.2.2 Notification notify and notifyAll are not lowered. JVM notify chooses an arbitrary waiter; notifyAll wakes all waiters, which then reacquire the monitor one at a time. WaitNotification.publish changes guarded state before notifyAll.
      17.2.3 Interruptions Board thread interruption is not lowered. On the JVM, interruption sets the status; an interrupted wait/sleep throws InterruptedException and clears it. Interruption demonstrates restoring the status when an exception cannot be propagated.
      17.2.4 Wait/notification/interruption races Not applicable on boards because neither wait sets nor interruption are exposed. On the JVM a notified-and-interrupted waiter may return normally with a pending interrupt or throw; it may not clear the interrupt and return normally, and notification cannot be lost. Covered as a specification rule rather than a deterministic board test because both race outcomes are legal.
      17.3 Sleep and yield Both are supported scheduling points. As required, neither releases a monitor nor creates a Java Memory Model synchronization edge. SleepAndYield prints monitor retained true.
      17.4.1 Shared variables Fields and array elements are shared; locals and parameters remain thread-confined. All examples keep shared state in fields or arrays and worker-local expected values in locals.
      17.4.2 Actions Ordinary reads/writes, volatile reads/writes, monitor actions, thread start, thread termination detection, and serial output are represented. Thread divergence is specification machinery rather than a terminating board test. The examples below exercise each supported action kind.
      17.4.3 Program order and sequential consistency Juno executes one task at a time and provides a stronger, sequentially consistent implementation. Portable code must still be correctly synchronized. LostUpdates contrasts a racy compound action with monitor, lock, and atomic updates.
      17.4.4 Synchronization order Volatile, monitor, start, and join synchronization edges are supported. Default zero initialization occurs before Java code runs. Interrupt edges are unavailable because interruption is unsupported. MonitorHappensBefore, VolatileHappensBefore, and ThreadStartAndJoin.
      17.4.5 Happens-before Monitor unlock/lock, volatile write/read, start, join, program order, and transitivity publish the expected values. A data race remains a bug even when Juno's single-core execution happens to hide it. The three happens-before examples each print 42; LostUpdates documents the racy counterexample.
      17.4.6–17.4.7 Executions and well-formedness These sections define how a specification validates an execution; they are not separate runtime APIs. Juno's compiler/runtime must only produce well-formed executions. Cross-checks run the examples on OpenJDK and on generated target code.
      17.4.8 Causality Values cannot arise solely from circular reasoning between racy reads and conditional writes. Causality prints out of thin air false.
      17.4.9 Observable behavior and nontermination Serial calls are external actions. Hangs are valid observable outcomes for deadlock or infinite execution, but an automated conformance example must terminate, so the suite does not deliberately hang a board. DiningPhilosophers avoids deadlock with a global lock order.
      17.5 Final fields Constructor-assigned final fields provide safe immutable state even when the reference publication itself is racy. The following rows separate ordinary freeze semantics from JVM-only reflective and System-stream exceptions.
      17.5.1 Final-field semantics Constructor exit freezes each final field. The guarantee extends to the initialized state reached through a final reference. FinalFieldPublication checks a final primitive and an array reached through a final field, then prints final value 42 when its deliberately racy reader observes the reference. Not observing the reference is allowed.
      17.5.2 Reads during construction Reads in the constructing thread follow normal program order: a read after assignment sees the assigned value. Java's definite-assignment rules prevent an ordinary constructor from reading its own blank final before assignment. The Value constructor assigns answer before the object can be published.
      17.5.3 Subsequent modification Reflection/deserialization mutation of final fields is not in Juno's closed-world subset. Portable board programs never mutate a final after construction. Marked unsupported rather than emulated with weaker semantics.
      17.5.4 Write-protected fields The special JVM treatment of System.in, System.out, and System.err is not applicable: Juno serial I/O uses Serial, and System.setIn/setOut/setErr are not lowered. No board test; these JVM globals are outside the board API.
      17.6 Word tearing Distinct fields and array elements are updated independently, including adjacent bytes on AVR. WordTearing prints word tears 0.
      17.7 double, long, and reference atomicity References and volatile 64-bit values are atomic. Juno also keeps non-volatile 64-bit fields whole while its scheduler is active, which is stronger than the minimum JLS guarantee. ReferenceAtomicity prints invalid references 0; VolatileLongAtomicity prints torn longs 0.

      Board matrix

      Target Compile and link Runtime execution
      UNO R4 WiFi Supported Physical board, or Cortex-M4 QEMU for the language/runtime layer
      UNO Q Supported Physical board; Cortex-M4 QEMU uses a stand-in for the Zephyr scheduling port
      UNO WiFi Rev2 Supported Physical board, or simavr for the AVR language/runtime layer
      Classic UNO R3 Not applicable The board has only 2 KiB SRAM and intentionally exposes no task scheduler; Juno rejects monitor/lock concurrency for it instead of silently weakening the semantics

      The annotation on every board-ready example names the three supported targets, so the normal language-example tests compile each class once per target. The Arduino CLI integration profile then builds and links the generated sketches with each target's real Arduino core. QEMU and simavr compare generated-code output with OpenJDK for the runtime layer; real hardware remains the final check for each scheduler port.
